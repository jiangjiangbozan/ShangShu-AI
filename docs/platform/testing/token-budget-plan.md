# 百炼额度排期与语料资产方案

> 场景：`qwen3.7-text-embedding-flash` 与 `qwen3.7-text-rerank` 两个模型额度即将到期，需要在到期前把剩余额度转成**一次性、可沉淀、可复用**的资产，而不是消耗在线上调用里。
> 数据基准：2026-11-27 实测单价 + 知识库入库统计。

## 1. 额度现状

用户提供的剩余额度（2026-11-27）：embedding **744,040 / 1,000,000**，rerank **671,620 / 1,000,000**。

本次批量任务实际消耗：

| 模型 | 消耗来源 | token |
|---|---|---|
| embedding | 批次 C 入库（72 篇 / 775 切片） | 137,175 |
| embedding | kb4 向量空间修复（747 片原地重嵌入） | 134,484 |
| **embedding 小计** | | **271,659** |
| rerank | 单价实测（3 次探针） | 16,046 |
| rerank | 错误知识库评测（约 17 题，已止损） | 约 88,600 |
| rerank | kb1 50 题正式评测 | 260,500 |
| **rerank 小计** | | **约 365,100** |

预计剩余：embedding **约 472,000**，rerank **约 306,000**。

> 本机 `sys_llm_log` 不记录 embedding / rerank 调用，额度以百炼控制台为准；上表按接口返回的 `usage.total_tokens` 累加。

## 2. 单价实测（`dev/rag-eval/probe_usage.py`）

| 场景 | 输入规模 | 实测 token | 备注 |
|---|---|---|---|
| rerank（旧配置） | 10 候选 × 1,200 字符 | 7,710 | 每候选约 771 token |
| rerank（新配置） | 10 候选 × 800 字符 | **5,210** | 省 32.4%，判别结论一致 |
| rerank（小批量） | 6 候选 × 800 字符 | 3,126 | 每候选约 521 token |
| embedding（纯中文） | 1,200 中文字符 | 766 | 0.638 token/字符 |
| embedding（中英混合语料） | 492,982 字符（kb4 官方文档） | 134,484 | 0.273 token/字符，英文与代码 token 效率更高 |

结论：**中文纯文本 embedding 约 0.64 token/字符，含英文/代码的技术文档约 0.27 token/字符**。

### 2.1 800 字瘦身的质量验证

同一套 50 题（kb1）、同一链路，只改 `max-candidate-chars`：

| 配置 | Recall@5 | MRR | nDCG@5 | 命中率 | 单次精排 token |
|---|---|---|---|---|---|
| 1,200 字符 | 0.940 | 0.845 | 0.870 | 94% | 7,710 |
| **800 字符** | **0.960** | **0.857** | **0.884** | **96%** | **5,210** |

结论：截断到 800 字符不仅省 32.4% token，指标还小幅上升（rerank 判别更聚焦于开场语义），可以放心长期保留。详细数据见 `rag-eval-slim-report.md`。

## 3. 剩余额度折算能力

- embedding 剩约 472K → 可再入库 **约 74 万中文字符**（纯中文）或 **约 170 万字符**（中英混合技术文档），对应切片约 800~1,100 片。
- rerank 剩约 306K → 按新配置 5,210 token/次，可跑 **约 5.9 万次**精排；折算评测：**约 58 题**全链路评测。

### 4.1 修复记录：kb4 向量空间错配

批次 B 入库时后端仍用 Ollama `nomic-embed-text`，747 条 kb4 向量与线上 DashScope 查询向量不在同一空间，检索必然失效（实测 nDCG 全为 0）。已用 `reembed.py --kb-id 4` 原地重算 747 条（492,982 字符 / 134,484 token / 20 秒），分片 id 与文本不变，历史评测集仍可用。

## 5. 剩余额度排期建议

按"先补语料、再换质量、最后留缓冲"的顺序：

1. **批次 D：补齐中文官方文档（预计 embedding 120K~200K）**
   - 候选源（当前网络可直连）：Kubernetes 中文站剩余 tasks/tutorials 分区（还有 200+ 篇）、Vite 中文站（cn.vitejs.dev）、Element Plus 中文站。
   - 目标：kb5 从 72 篇扩到 130~150 篇。
2. **评测集扩容到 100 题（预计 rerank 260K，与已完成的 50 题共 150 题）**
   - 新增中文 K8s 主题题目，覆盖批次 C 语料。
3. **缓冲区（保留）**
   - embedding 留 100K、rerank 留 50K 应对线上真实调用与临时验证。

## 6. 明确不做（避免额度打水漂）

- **不做 N² 两两相似度**：1,930 切片两两比对约 186 万次调用，额度瞬间烧光且无可复用产物。
- **不把 rerank 挂在每轮对话**：单次 5,210 token，1,000 轮就是 5.2M，额度耗尽后线上直接降级。
- **不指望这两个模型生成内容**：它们是表征模型与判别模型，只能产出向量与相关性分数。

## 7. 复现与成本控制

```powershell
# 抓取批次 C（K8s 中文文档，可改 --limit）
python dev/rag-corpus/fetch_k8s_zh.py --limit 85

# 入库到「中文技术文档库」
python dev/rag-corpus/upload_corpus_c.py

# 指定知识库原地重嵌入（修复向量空间错配）
python dev/rag-eval/reembed.py --kb-id 4

# 实测单价（消耗约 1.7 万 token）
python dev/rag-eval/probe_usage.py
```

成本控制要点：`rag.rerank.max-candidate-chars` 已从 1,200 降到 800，单次精排 token 下降 32%；候选数 `candidate-n` 保持 10，不建议再降（会损失召回上限）。
